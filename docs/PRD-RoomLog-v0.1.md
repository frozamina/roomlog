## 1. 背景与问题

租房决策存在三个信息断层，现有工具一个都没解决：

**断层一：记忆会衰减。**
住了两年的房子，搬走三个月后你只记得「还行」或「不想再住」。隔音到底差到什么程度、冬天水压到底能不能洗澡、下午几点开始有阳光——这些当时清晰无比的感受，会迅速坍缩成一个模糊的形容词。下次租房时，你无法拿它当依据。

**断层二：支出是黑箱。**
房租是显性成本，水电网物业是隐性成本。一年下来，一套「月租 1800」的房子可能比「月租 2000」的房子更贵——商水商电、冬天电暖、物业另收。没有逐月记录，你永远算不清真实的居住单价（元/㎡/月）。

**断层三：偏好不自知。**
人普遍高估自己在意的东西。你以为自己在乎采光，住进去才发现真正折磨你的是楼上半夜的脚步声。偏好不是想出来的，是住出来的——但前提是你记录过。

**现有工具的错位：** 记账 App 记不了房屋属性；备忘录字段散乱、无法比较；Excel 在手机上录入门槛过高，坚持不过三个月。

## 2. 产品定位

> **一句话：把每一套房子的客观条件、真实开销和你的真实感受沉淀成数据，让下一次租房有据可依。**

**是**：私人档案 + 决策辅助工具，离线优先，数据完全属于你。
**不是**：找房平台（不看房源、不签约、不撮合）、社交产品、通用记账 App。

三层价值，逐层递进：

| 层级 | 名称 | 用户获得 | 产品对应 |
|---|---|---|---|
| L1 | 记录 Recall | 随时查到某套房的任何细节 | 房源档案、条件字典、照片 |
| L2 | 复盘 Reflect | 知道钱花在哪、房子好在哪差在哪 | 月度账本、居所指数、时间线 |
| L3 | 决策 Decide | 知道自己真正在意什么，新房子能不能达标 | 偏好权重、红线清单、候选房匹配度 |

L3 是产品的灵魂。市面上没有一个工具会告诉你「你的红线条件是隔音 4 分以上」——而这个结论只能由你自己的历史数据算出来。

## 3. 目标用户与场景

**主用户画像**
- 都市租客，25–35 岁，2–5 年内预计换房 1–3 次
- 对居住品质敏感，会为「住得舒服」多付一点钱
- 有过「租完才后悔」的经历，不愿意再踩第二次
- 习惯用数据说话，能接受一次性录入 10 分钟的成本

**三个核心场景**

| 场景 | 触发 | 用户动作 | 产品支撑 |
|---|---|---|---|
| S1 入住建档 | 签完合同、搬进去第一周 | 拍照片、录条件、打分 | 分步表单，10 分钟建完一套档案 |
| S2 每月记账 | 收到水电账单 / 交房租 | 录 4 个数字，30 秒 | 极简录入，自动算总量与环比 |
| S3 换房决策 | 准备搬家，看新房 | 查历史、比候选、看红线 | 房源对比、匹配度评分 |

**非目标场景（明确不做）**：房源搜索、合同签署、租金支付、室友分账（V2 再议）。

### 4.2 M1 房源档案 · 条件字段字典

一套房子 = 一次居住经历（同一房源租两次 = 两条记录，便于对比涨租）。带 ★ 为必填。

**A 组 · 基本信息**

| 字段 | 类型 | 输入方式 | 说明 |
|---|---|---|---|
| ★ 房源名称 | 文本 | 键盘 | 如「翠湖苑 3 栋 1202」 |
| 地址 | 文本 + 坐标 | 地图选点（P1） | 用于算通勤距离 |
| ★ 月租 | 数字 | 数字键盘 | 元/月 |
| ★ 起租日 / 退租日 | 日期 | 日期选择 | 退租日空 = 在住 |
| 面积 | 数字 | 数字键盘 | ㎡ |
| ★ 户型 | 枚举 | 步进器 | X室X厅X卫 |
| 楼层 / 总层 | 数字 | 数字键盘 | 3/18 |
| 朝向 | 枚举 | 芯片单选 | 东南/南/西南/正西/北… |
| 建成/装修年份 | 数字 | 数字键盘 | 判断老旧程度 |

**B 组 · 舒适度实测（核心，1–5 分 + 备注）**

| 字段 | 类型 | 说明 |
|---|---|---|
| ★ 隔音（窗外） | 1–5 | 临街、高架、学校、施工、夜市 |
| ★ 隔音（楼板/邻户） | 1–5 | 楼上脚步声、隔壁说话、管道声 |
| ★ 采光 | 1–5 | 附「日均直射日照时长（小时）」 |
| 通风 | 1–5 | 能否形成穿堂风 |
| ★ 水压 | 1–5 | 附「淋浴是否有劲」布尔标记 |
| 潮湿/霉味 | 1–5 | 反向分：5 = 完全不潮 |
| 保温/西晒 | 1–5 | 夏天是否热得待不住 |
| 噪音源标签 | 芯片多选 | 临主干道/高架/地铁/学校/工地/夜市/铁路 |

**C 组 · 硬件与家电**

| 字段 | 类型 | 说明 |
|---|---|---|
| ★ 电梯 | 枚举 | 有梯 / 步梯（附台阶层数） |
| 热水器类型 | 枚举 | 燃气/电热/集中供热/太阳能 |
| 燃气 | 布尔 | 有无管道燃气（决定能不能做饭） |
| 空调 | 数字 + 枚举 | 几台、是否变频 |
| 家电清单 | 勾选 + 各自 1–5 分 | 冰箱、洗衣机、油烟机、灶具、微波炉、电视、衣柜、床、书桌、沙发 |
| 阳台 | 枚举 | 无 / 有（附朝向） |
| 卫生间 | 枚举 | 独卫 / 合卫，是否干湿分离 |

**D 组 · 费用规则（决定真实成本）**

| 字段 | 类型 | 说明 |
|---|---|---|
| ★ 水电性质 | 枚举 | **民用 / 商用 / 二房东加价**（关键，直接影响电费单价） |
| 电费单价 | 数字 | 元/度，民电约 0.55–0.65，商电常 1.0–1.5 |
| 水费单价 | 数字 | 元/吨 |
| 押付方式 | 枚举 | 押一付一 / 押一付三 / 押二付一… |
| 中介费 | 数字 | 通常为半月或一月租金 |
| 物业费 | 数字 | 元/月，是否含在租金内 |
| 管理费 / 卫生费 | 数字 | 二房东常见的隐性收费 |
| 网络费 | 数字 | 元/月，是否含宽带 |
| 车位费 | 数字 | 元/月 |
| 合同起止 / 最短租期 | 日期 + 数字 | 判断灵活性 |
| 续租涨幅 | 百分比 | 历史涨幅，警惕房东习惯 |

**E 组 · 周边与通勤**

| 字段 | 类型 | 说明 |
|---|---|---|
| ★ 通勤时间 | 数字 | 门到门分钟数（最重要的一项周边指标） |
| 最近地铁/公交 | 文本 + 距离 | 站名 + 步行米数 |
| 生活配套 | 数字（步行分钟） | 菜场、超市、医院、药店、健身房、公园 |
| 外卖/快递 | 枚举 | 送上楼 / 需下楼 / 有快递柜 |
| 治安与夜间照明 | 1–5 | 主观感受 |

**F 组 · 人际与规则**

| 字段 | 类型 | 说明 |
|---|---|---|
| 房东响应 | 1–5 | 报修后多久到、态度如何 |
| 是否可养宠 / 可做饭 / 可改造 | 布尔 | 影响生活方式 |
| 室友/邻里情况 | 文本 | 合租时必填 |
| 一句话总结 | 文本（≤ 60 字） | 三年后你只会看这一句 |
| 会不会再租 | 枚举 | 会 / 不会 / 看情况 |
| 后悔指数 | 1–5 | 事后回看，最能校准偏好 |

### 4.3 M2 费用账本

**月度账单字段**

| 字段 | 说明 |
|---|---|
| 月份 | YYYY-MM（每月一条） |
| 房租 | 元 |
| 水费 | 用量(吨) + 单价 + 金额（录任意两项自动补第三项） |
| 电费 | 用量(度) + 单价 + 金额（同上） |
| 燃气费 | 用量(方) + 金额 |
| 物业费 / 管理费 | 元 |
| 网络费 | 元 |
| 其他 | 保洁、维修、车位、耗材，可自定义条目 |
| 账单截图 | 可选，1 张 |

**自动派生指标（不需要用户算）**
- 月度总支出 = Σ 全部条目
- 日均居住成本 = 总支出 ÷ 当月天数
- 单位面积成本 = 总支出 ÷ 面积（元/㎡/月）—— 跨房源比较的唯一公平口径
- 水电占比 = (水+电) ÷ 总支出 —— 超过 25% 就是隐性成本警报
- 环比 / 同比、全年累计、夏季冬季用电峰值对比
- 单价合理性提示：录入电费单价 > 0.8 元/度时提示「疑似商电或二房东加价」

### 4.4 M3 洞察引擎

**① 居所指数（0–100）**
各维度体验分（1–5）× 该维度在意度权重（用户录入时标记 1–3），加权归一化后映射到 0–100。用于列表页一句话排序，也让「好房子」有可比较的数字。

**② 偏好权重画像**
不再让用户凭感觉填权重，而是从行为数据反推：
- 显性信号：录入时每个维度的「在意度」选择
- 隐性信号：退租时「后悔指数」高的房子，其低分维度权重自动上调
- 输出：横向条形图 + 一句人话结论，例如
  > 「过去 3 套房里，隔音的在意度是最高档，但实际得分最低（平均 2.3）。这是你的红线。「采光」你在意程度中等，实际也都达标——不必为它多付租金。」

**③ 红线条件**
取「在意度 Top 3 × 历史均分 < 3.0」的维度，生成下次看房的必查清单（Checklist），可在看房时逐项打勾。

**④ 候选房匹配度**
对一处在看的新房打分 → 用你的权重计算匹配百分比 → 输出「82% 匹配，但水压 2 分低于你的红线 4 分」。

### 4.5 M4 数据安全

- 全部数据存本地 SQLite，App 不联网（除可选的云备份）
- 一键导出 JSON（完整结构，可再导入）+ CSV（账单，可喂给 Excel）
- 首次启动引导「设置自动备份到手机本地目录」
- V2 可选：应用锁（指纹）、云备份

## 6. 关键流程

**流程 1 · 首次使用（冷启动）**
空状态页（不空白，给一句引导）→ 「建立第一套档案」→ 基本信息系统建议只填 5 项（名称/月租/面积/户型/起租日）→ 先建档，其余可后补 → 建档完成即给一个居所指数（此时基于自评，标注「样本不足，多记几套房后更准」）。

> 原则：任何字段都不要阻塞流程。宁可建档不完整，也不要让用户在第一分钟放弃。

**流程 2 · 每月记账（30 秒）**
账单 Tab → 当月卡片已预填上月数字（复用上次 + 房租固定项）→ 只改水电用量 → 保存 → 自动更新总额与环比。
> 这是留存的关键。录入门槛高于 30 秒，这个 App 就会在第三个月死掉。

**流程 3 · 换房复盘**
退租 → 房源详情弹出「退租复盘」→ 填后悔指数、会不会再租、一句话总结 → 生成该房源的「结算报告」→ 结论自动汇入偏好画像 → 红线清单更新。

## 7. 交互与设计原则

1. **一屏一个焦点。** 详情页的第一视觉中心是「居所指数」，账单页是「月度总额」，洞察页是「你最在意的三项」。
2. **数字优先。** 所有关键指标用大字号 tabular 数字（等宽），保证纵向对齐好扫读；单位小字紧跟其后，不换行。
3. **表单分步、可跳过。** 单屏不超过 6 个字段；每步底部有「跳过」文本按钮。
4. **评分优于填空。** 主观项一律用 5 点分段条而非文字输入，降低认知负担，也让数据可计算。
5. **触控 ≥ 44px。** 拇指区（屏幕下方 1/3）只放主操作。
6. **空状态有引导，错误提示贴字段。** 不用弹窗报错。
7. **离线零等待。** 无网络请求、无 loading 骨架屏超过 200ms；所有写入即时生效。
8. **尊重无障碍：** 对比度 ≥ 4.5:1，状态不只靠颜色区分，支持系统字体放大与减少动效。

## 8. 技术方案

### 8.1 选型建议（v0.2 调整）

技术栈从 Flutter 改为 **Web + 原生壳**，原因是工程上的：本机没有 Flutter / Java / Android SDK，写 Flutter 意味着每一行代码都无法在本地验证，只能等 CI 盲跑；而 Web 层可以本地真实渲染、逐屏走查，且视觉与已确认的设计稿天然一致。

| 层 | 方案 | 理由 |
|---|---|---|
| 框架 | Vue 3 + Vite | 组件化；构建产物是纯静态文件，可直接被 Capacitor 装入 |
| 原生壳 | Capacitor 7 | 把 web 产物打包成 APK；后续需要震动、文件、分享等能力时有现成插件 |
| 存储 | localStorage（JSON 文档） | 单人使用、数据量小（10 套房 × 36 月 ≈ 数百条，< 1MB），同步读写、零依赖、导出即备份 |
| 图表 | 手写 SVG / CSS | 不引第三方图表库，体积与视觉都可控 |
| 构建 | GitHub Actions | ubuntu runner 自带 Android SDK，`gradlew assembleDebug` 直接出包 |

> 存储这一层补充说明：原规划是 SQLite，但按月聚合、跨房源对比的数据量用内存 JSON 一次性过滤完全够用，引入 SQLite 只会增加原生插件与 CI 复杂度。等记录量级超过万条再迁移。

### 8.2 APK 产出路径（已确定：B 云端构建）

```
本地 npm run build  →  dist/  →  npx cap sync android  →  push  →  Actions 跑 gradlew assembleDebug  →  下载 app-debug.apk  →  手机安装
```

- Debug 包可直接安装，无需签名证书；安装时需允许「安装未知来源应用」
- 推送授权使用个人访问令牌（fine-grained，仅限该仓库 Contents 读写），不落盘、用完可吊销
- 未来要正式签名发布，把 keystore 放进 GitHub Secrets 即可

### 8.3 非功能指标
- 冷启动 < 1.5s，页面切换 < 200ms
- APK 体积 < 15MB（Web 方案通常 6–8MB）
- 支持 Android 7.0+（minSdk 24）
- 数据量级 3 年内 < 5MB
